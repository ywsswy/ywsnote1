- MFA = Multi-Factor Authentication，多因子认证，登录时要求提供两个或以上不同类型的"凭证"才能通过（两个就叫2FA），常见密码+OTP；

- SSL是协议（Secure Sockets Layer），后来被重命名为TSL（Transport Layer Security），TLS 1.0通常被标示为SSL 3.1，TLS 1.1为SSL 3.2，TLS 1.2为SSL 3.3
- 对称密码：分组密码(DES,IDEA,AES)和流密码(RC4)；缺点秘钥管理困难
- 非对称密码：RSA、ELGamal、椭圆曲线ECC；缺点加解密效率低；（这世上为什么会存在非对称的密码呢，一个神奇的例子是假如一个9位数字是明文，运算就是乘法，私钥可以是19019，公钥可以是52579；明文*先公钥*先私钥|截断后9位 = 明文*先私钥*后公钥|截断后9位 = 明文，原因就是19019*52579=1000000001）
（1）先用私钥“运算”（这里的运算在密码学领域不能叫做加密因为公钥是公开的-运算了也没有秘密-只能叫做 发送方进行数字签名），再用公钥运算（接收方进行验证签名/解签名）；
（1.1）接收方怎么验证签名呢？见下面数字证书的Signature字段说明；
（2）先用公钥加密（现实生活中有点像信箱的例子），再用私钥解密：防偷看；
- 计算机可以在多项式时间复杂度内解决的问题：P类问题（Polynomial），不可解决则是NP
- Hash函数：只有加密，没有解密：（MD5、SHA）：消息摘要/指纹；
- 符合 X.509 标准的数字证书格式：
（1）主体内容：公钥（Subject Public Key Info，谁的证书就是谁的公钥，CA的根证书就是CA的公钥，服务器的证书就是服务器的公钥）、有效期Validity、颁发者Issuer、颁发目标Subject、扩展字段；
（2）数字签名Signature：颁发者私钥签名（Hash（<上面主体>）），也就是说先把主体信息算一次消息摘要，但是这个指纹并不会直接传输，而是要再进行数字签名（搞两个步骤的目的应该是为了签名长度一致）再传；验证B证书是否可信的方法就是看B证书的颁发者A，用A的公钥（假如A是CA根证书机构-那A的公钥就可以在系统预装的CA根证书里可以取到）而不是B证书里的公钥解签名，解出来的是hash1，然后再用同样的hash算法对证书主体算一次hash2，如果hash1 = hash2，说明可信；（ps：这里的hash并不直接称为证书指纹？因为严谨来说证书指纹是对证书的全部内容hash，而不是只对部分主体hash；）
- 数字证书的三种level：
-- CA根证书（中央印章-自签发一般会预装到系统设备里，可以理解为一个文件或者一个数据结构）：证书的 颁发者和颁发目标相同；无需写域名；CA根证书的数字签名没卵用，因为CA根证书最特殊的点是自签名的，所以黑客如果改了CA根证书的公钥，自然也能改数字签名，用改了的签名验证改了的公钥没有意义，这个字段单纯是为了符合X.509 标准；
-- CA中间证书（地方印章-由CA根证书或比自己更高级的CA证书签发）；起到安全缓冲隔离，避免直接用CA根证书给所有服务器签发，万一泄漏根CA的密钥，故障影响面太大；
-- HTTPS网站的服务器证书（个人身份证-由CA中间证书签发）：扩展字段的SAN字段里会写域名；浏览器会校验这个字段根域名是否相符； 
- https的安全原理（TSL协议有很多版本和使用方式都不同，这里只举一个简单例子）：
```
物理上有三个位置：【客户端】 【中间网络设备】 【服务端】
https解决的是“让 中间网络设备 无法解密（读） 无法篡改（写）两端传输的数据”（原始http传输的是明文，包括URL 的路径和查询参数）
思路是，双方先明确使用一个密钥（对称的-运算速度快，叫会话密钥），然后后续传输原始数据时都用这个会话密钥来加密；
这个会话密钥是客户端自由生成然后告诉（就是传输，当然这个阶段传输的数据会用服务端公钥加密）给服务端的（可以这么简单理解-虽然实际会更复杂）；
关键在于（1）怎么保证客户端拿到真实的未被篡改的服务端公钥，做到这点就不怕后续数据被截获-因为中间人没有私钥无法解密；（2）服务端拿到真实的未被篡改的会话密钥；
第（1）点靠服务端开发者建站时向可信的第三方机构CA申请数字证书（提供的材料-CRS-包括我持有的IP、我想要给哪个域名加证书、我的公钥信息；得到的证书文件后缀是.crt/.pem里面也会放中间CA证书-证书链，自己的私钥文件后缀是.key），然后用户访问时返回给客户端验证来保证；
这就解释了为什么不要自签SSL证书，因为中间人可以做一个假的服务器SSL证书与用户通信，虽然浏览器会警告用户此证书不受信任，但是用户用自签证书已经习惯性点击“继续浏览”了，这样中间人攻击轻而易举的实现了，就可以截获用户输入的机密信息。
第（2）点，退一万步讲，就算服务端拿到的是中间人的假的会话密钥，成功跟中间人建立了连接，但是服务端的危险操作，肯定还是要输入用户名和密码，这个中间人肯定也没法输入对；
```
